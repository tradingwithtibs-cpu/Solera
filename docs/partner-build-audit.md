## wallet-auth

Partner build (/Users/tibet/Desktop/solerafinal) has NO Supabase, NO backend and NO password auth: sign-up/login are localStorage-only (keys 'solera-accounts-v1' and 'solera-demo-state-v1'), login is an email lookup with no secret, and the wallet "sign-in" signature is discarded and never verified. Wallet detection (engine.js:878-881) is actually correct and lazy (checked at click time, window.phantom.solana first), so "Get Phantom" only appears when provider() is null; reproduced on http://127.0.0.1:8080 that a Phantom-shaped provider flips the label to "Connect Phantom" and connect succeeds. The only way an installed extension yields "Get Phantom" is an environment where it does not inject, and the build's README tells the user to open index.html directly (file://), where extensions do not inject; the label at engine.js:957 does not branch on isFile so it still reads "Get Phantom" there. Additional UX cause: the "Live · mainnet" button never offers to connect; it silently assigns a hard-coded demo wallet (engine.js:1029). Live mode never signs anything: with a kind:'phantom' wallet, a fill made 0 provider calls and 0 network calls and deducted practice cash with a random fake tx hash. The live Next.js app already has everything the partner build fakes: wallet-adapter with Phantom/Solflare/Wallet Standard + iOS deeplink adapter, mode gating that requires a connected wallet, ed25519-verified profile claims written to Supabase with RLS, and 30-day HMAC session tokens for chat. It has no Supabase Auth; email+password sign-up requires adding @supabase/ssr, an auth.users-linked identity column on profiles/messages, and extending /api/profile and /api/session to accept a Supabase session as an alternative to a wallet signature.

## plans-agent

The partner build's "plans + agent" surface (/Users/tibet/Desktop/solerafinal/assets/plans.js, 177 lines) is a client-only regex parser plus a localStorage rule engine. Every plan trigger, every agent.order(), every ?plan= URL and every postMessage lands in engine.js fill(), which mutates practice cash/holdings and fabricates a tx id; nothing is signed or sent in any mode, and help() says so.
